# Preparing a public repository

Public source contains reusable code, documentation and synthetic fixtures. All installation-specific data belongs under ignored `.local/`: project registries, governance, campaigns, approvals, machine configuration, logs, reports, screenshots and backups. Never include it in public issues, pull requests, comments or commit messages. An explicit force-add can override `.gitignore`, so the public-scope check is part of `npm run check` and the installed pre-commit hook.

Removing tracked files does not erase previous commits. Before changing an existing repository's visibility, prepare a separately reviewed clean publication history or a fresh repository from an audited source snapshot. A normal cleanup commit leaves earlier campaign blobs, commit messages, author metadata and old branches reachable.

Repository publication also exposes issues, pull requests, comments, attachments, releases and other metadata. Review these separately; a clean code snapshot does not sanitize them. Do not change visibility, force-push rewritten history or delete remote records as part of a source cleanup without explicit authorization for that concrete action.

## Private files

Keep declarations under `.local/campaigns/`, governance under `.local/governance/`, and runtime state under `.local/supervisor/`. Legacy ignored paths remain supported, but new installation data goes under `.local/`. Never use real campaign records as fixtures. `npm run setup:local` creates the redistributable governance starter without registering or authorizing a project and refuses to replace existing governance.

## Checks

Run `npm run check`, review the staged file list and inspect the complete proposed public snapshot. Privacy checks must inspect the proposed content without printing secret values. Synthetic examples must use fictional organizations, repositories, paths and identities.

`npm install` installs the repository's pre-commit and pre-push privacy hooks. Existing custom hooks are preserved; chain these checks into them before publishing. The staged-content check rejects private paths, common credential formats, personal installation paths and references to the upstream owner's other repositories. It reads Git's index, so cleaning the working file alone cannot conceal staged content. The push hook also checks new commit messages and intermediate trees, including disclosures deleted in a later commit. It checks new commits relative to the destination and the full ancestry for a new branch or tag. It also checks filenames, ref names and tag annotations; tags must resolve to commits. It does not certify already-published destination history.

Keep installation-specific names out of the public rules too. An optional ignored `.local/publication.json` holds `{"privateTerms":["fictional-private-project","fictional-private-host"]}` for local text checks. Use your actual private identifiers only in that local file. Add `"repositoryRoots":["<repos-root>"]` to make the name of every Git checkout in that folder private as well, so a project you add later is covered without editing the list; names shorter than five characters, names in `"ignoreRepositories"` and the checking checkout's own name are left out. Put a checkout with a generic name (such as `notes` or `scripts`) in `"ignoreRepositories"`. Only the commit and push checks use these names: the supervisor's own publications to a project name that project and keep to `privateTerms`. In those publications (pull request titles and bodies, comments and notes) two kinds of private term are dropped for that project only and still bind every other project. A term contained in the project's own repository name (after the owner) is dropped, ignoring case and treating `-` and `_` alike. A term the project's tracked files already hold at the tip of its base branch, as the supervisor fetches it before publishing, is dropped too: its readers can already read it there. Only that base counts, never the verified head or any other commit a worker made, so a worker cannot make a term publishable by writing it into its own change. When the base cannot be read, or the search fails or times out, every term binds. Neither rule changes this repository's own commit and push checks. A linked worktree uses the settings of its main checkout. Findings print neither the matched values nor private filenames. Tests construct synthetic credential shapes at runtime rather than placing complete token-shaped literals in source.

The checks also refuse binary files (images, PDFs, archives, office documents, fonts and any file with NUL bytes), because a screenshot can show a person, an email address or a private window that no text check reads. A binary file may be published only when its blob id is listed in `.public-binaries`. Open the file and confirm it shows no private data before you add `<blob id> <path>` there; `git rev-parse :<path>` prints the id of a staged file. The refusal names only blob ids.

Git hooks see only commits. Text that an agent posts with `gh` (pull request bodies, issue comments, API writes) never passes through them. `node scripts/claude-guard/install.mjs` installs a Claude Code PreToolUse hook for the current user. Before a `git push` or a `gh` write to a public GitHub repository, in any project, it checks:
- the command text, the files the command sends, and the commits being pushed;
- the private terms, the names of the checkouts under the repository roots, personal paths and session links;
- `--no-verify`, and binary files not in that repository's `.public-binaries`.

It refuses the call when any check fails, and leaves private repositories alone. Its settings stay in `~/.claude/hooks/public-guard.json`, outside the repository (see `scripts/claude-guard/public-guard.example.json`). [PUBLIC_GUARD.md](PUBLIC_GUARD.md) covers setup on a computer, the installation check (`node scripts/claude-guard/check.mjs`), the settings and what to do when a guard refuses.

Hooks and pattern scanners are additional checks, not proof that arbitrary text is safe. Do not bypass them. Review source, assets, every proposed commit and public metadata before publishing. Source cleanup cannot erase existing Git objects, GitHub edit history or downloaded copies; history and remote-record cleanup require an explicit reviewed plan.
